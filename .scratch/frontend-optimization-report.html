OGSystem · 前端审计

页面端优化建议

覆盖 Visualizer 专业控制台与 Team Site 产品站两个前端面。按影响面与改动成本分级，从交付效率到架构可维护性逐项分析。

5.86 MB Visualizer 浏览器总加载量（未压缩）
9107 client-app.ts 行数（单文件）
115 innerHTML 调用（两端合计）
已实现 Team Site 缓存 / 压缩策略
01

传输与交付

关键

交付压缩与缓存已实现，继续核对 Visualizer

Team Site server 已协商 Brotli/gzip，并返回 Content-Encoding、Vary: Accept-Encoding 和缓存策略；带版本摘要的资源使用长期 immutable 缓存。Visualizer 的静态资源仍需单独核对缓存策略，因此这里不再把 Team Site 的交付能力列为缺陷。

资源原始大小
assets/client-app.js860 KB
studio-client/studio-graph.js5.0 MB
page-shell-styles（内联 CSS）147 KB
Team Site styles.css + shell.css192 KB
当前结论
Team Site 的压缩和版本化缓存已落地；后续优化重点是确认 Visualizer 资源的缓存策略，以及对仍未构建的 Visualizer client-app.js 做独立的产物优化。
关键

Visualizer JavaScript 与 Team Site CSS 的构建状态不同

Visualizer 的 client-app.js 仍由运行时脚本拼接，未进入独立的 minify 流程；但 Team Site 已通过 scripts/build-assets.mjs 使用 esbuild 生成 styles.min.css，并由 index.html 引用。报告只保留 Visualizer JavaScript 作为后续优化项。

建议
在 build:visualizer-client 脚本末尾对输出调用 esbuild 的 transform({ minify: true })。Team Site CSS 可用 esbuild 或 Lightning CSS 压缩。光 minify 即可减少 30-40% 的传输量。
重要

Studio Graph 按需加载已有但可更精细

Team Site 中 ensureStudioGraphBundle() 已做到懒加载 5MB 的图表引擎 — 这很好。但 Visualizer 端在页面初始化时即加载全部 client-app.js（含 Build、Operate、Review、Studio 全部面板渲染逻辑），无论用户当前只看哪个 tab。

建议
将 client-app.ts 按 console panel（Build / Operate / Review / Studio / Logs）拆分为独立模块，tab 切换时 import() 加载对应模块。初始加载只需 shell + 路由 + 当前 tab。
02

构建架构

关键

.toString() 序列化反模式

buildClientAppScript() 将约 130 个函数通过 fn.toString() 拼接成一个全局脚本字符串。这意味着：

① 无法 tree-shake — 即使某面板不需要某个 render 函数也全量包含
② 无法 source map — 浏览器调试时看到的是一行行序列化的匿名函数
③ 无法 minify 闭包内变量名 — minifier 无法安全重命名
④ 编译时无法检测运行时缺失 — 函数引用的外部名在拼接时不做校验

建议
用 esbuild 直接 bundle client-app.ts 的一个浏览器入口点，输出 ESM 或 IIFE。现有的 build:studio-client 已展示了这个模式（用 esbuild 打包 studio-client/main.ts）。对 client-app 做同样处理，配合 --splitting 可自动实现代码拆分。
重要

9107 行单体 client-app.ts

全部客户端逻辑（路由、状态初始化、全部 panel 的事件绑定、SSE 流处理、Studio 图编辑命令、i18n 协商、主题切换）集中在一个文件。修改任一功能都需要在近万行中定位。client-renderers.ts（2896 行）和 page-shell-styles.ts（4905 行）也是同等量级。

建议
按功能域拆分：client-app-shell.ts（路由、主题、i18n）、client-build-panel.ts、client-operate-panel.ts、client-review-panel.ts、client-studio-panel.ts。每个模块导出一个 mount(container, state) 和 update(state)。这也为后续按 tab 的代码拆分铺路。
建议

Team Site 已有 CSS 构建步骤，JavaScript 仍保持模块化加载

Team Site 的 public/ 目录由 Node.js 静态服务，但 CSS 已由 build-assets.mjs 压缩并生成版本摘要；JavaScript 仍按入口和视图模块加载。当前可继续评估 JavaScript bundle 的收益，但不应再把 CSS 误报为未构建。

建议
保留现有 CSS 构建；若 Team Site JavaScript 继续增长，再以入口为边界评估 bundle 或更细粒度动态导入，避免重复引入已经存在的 CSS 构建能力。
03

渲染性能

重要

innerHTML 大规模使用

当前源码统计为 115 处 innerHTML 赋值（Visualizer 15 处，Team Site 100 处）。每次赋值都会销毁子树并重建 DOM，丢失焦点、滚动位置和已附加的事件监听器。在运行状态面板中，SSE 事件每秒多次触发面板重绘时尤为明显。

建议
分阶段改进：① 对高频更新区域（运行状态指标、日志面板、时间线）改用 textContent 或细粒度 DOM 更新；② 对整面板重建场景引入轻量 diff 或 morphdom（~3KB gzip），只修改变化部分；③ 长期可评估 Preact（~4KB）以获得声明式渲染和自动 diff。
重要

SSE 流事件缺少节流

Visualizer 通过 EventSource 订阅运行流，每个事件都可能触发面板 HTML 重建。在高吞吐运行中（多角色并发输出），UI 线程可能被密集的 DOM 重建阻塞。

建议
在 SSE 事件处理器中加入 requestAnimationFrame 节流：将事件写入内存队列，每帧只做一次批量 DOM 更新。已有的 StreamRefreshPlan 和 StreamCursorIndex 提供了良好的批处理基础设施。
建议

CSS 内联在 JS 模块中

page-shell-styles.ts 将 4905 行 CSS 作为模板字符串返回，在 HTML 的 <style> 中内联。这意味着：样式不能被浏览器独立缓存、无法并行下载、每次页面加载都重新解析。

建议
在构建时将 CSS 提取为独立的 assets/visualizer.css 文件，通过 <link rel="stylesheet"> 引入。配合内容哈希文件名和长期缓存，可大幅减少重复传输。
04

用户体验

重要

首屏加载体验

Visualizer 需要浏览器下载 860KB 的 client-app.js 后才能初始化界面。在慢网络下，用户会看到空白页面。当前有 renderLoadingSkeletonHtml() 但它是在 client JS 执行后才渲染的，无法覆盖 JS 下载期间的空白期。

建议
将骨架屏 HTML 直接写入服务端返回的 HTML 模板（page-shell-template.ts）中，在 <main class="main-stage"> 内放置一个静态骨架屏，JS 加载完成后替换它。同时给 <script> 标签加 defer 避免阻塞渲染。
建议

页面间状态丢失

Team Site 的 SPA 路由切换时，通过 hidden class 切换多个 .alternate-view 容器。每次路由切换后，之前的 view 可能被 innerHTML 重写而丢失表单输入和滚动位置。

建议
对需要保留状态的 view（如项目创建表单），在切出时序列化状态到内存对象，切回时恢复。或者保持 DOM 不销毁（当前已部分实现），只在数据变化时增量更新。
建议

移动端适配深度不足

Team Site 的 index.html 已有移动端导航按钮和侧栏折叠，但 Visualizer 的 Studio 图编辑面板（依赖 @antv/x6 画布交互）在触屏设备上的可用性有限。CSS 也缺少对小屏幕下 inspector 面板的自适应处理。

建议
Visualizer Studio 可标记为桌面优先工具（这是合理的产品决策）。在移动端访问时显示提示引导使用桌面端，并将 Build/Operate 等只读面板做好响应式处理以支持移动端查看运行状态。
05

安全与健壮性

重要

innerHTML 的 XSS 风险

虽然项目有 escapeHtml() 工具函数并在服务端模板中使用，但客户端 115 处 innerHTML 赋值中，仍需确认每处用户可控数据（角色名、项目名、任务描述）都经过转义。在 Team Site 的 app.js 中有 esc() 函数，报告应以当前计数为基准继续做覆盖率审计。

建议
① 对所有 innerHTML 赋值做一轮系统性审计，确认用户输入均经 esc() 处理；② 考虑引入 CSP script-src 头作为纵深防御；③ 长期用 DOM API 或模板引擎替代 innerHTML 可从根本上消除这类风险。
建议

错误边界缺失

客户端 JS 中的未捕获异常会导致整个应用停止响应。没有全局 window.onerror 或 unhandledrejection 处理器来降级展示或上报错误。

建议
添加全局错误处理器，在页面上显示友好的降级提示（如 "页面遇到错误，请刷新"），并将错误信息记录到 console 或可选的诊断 API。
06

优先级路线图

第一阶段 · 低成本高回报（1-2 天）

① HTTP 响应加 gzip 压缩 — 改动两个 server 文件，总加载量预计降 70-80%
② 静态资源加 Cache-Control 和 ETag — 消除重复请求
③ 构建输出加 minify（esbuild transform）— 再减 30%
④ 服务端 HTML 模板内嵌骨架屏

第二阶段 · 架构改善（1-2 周）

① 将 client-app.ts 的 .toString() 模式替换为 esbuild 直接 bundle
② 拆分 client-app.ts 为功能模块
③ 高频 innerHTML 改用细粒度 DOM 更新
④ SSE 事件加 rAF 节流

第三阶段 · 持续改进

① CSS 从 JS 模板字符串提取为独立文件
② 按 tab/panel 做代码拆分（code splitting）
③ innerHTML XSS 全面审计
④ 全局错误边界
⑤ 评估轻量 UI 库（Preact / morphdom）
