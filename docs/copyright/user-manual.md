# OGSystem 图形化智能体流程编排与运行管理系统

## 使用说明书

版本：1.0.0；材料属性：软件著作权登记文档鉴别材料工作稿；开发者、著作权人、完成日期：待权利人核实后填写。

## 1. 软件概述

OGSystem 是用于建模、校验和运行多角色智能体工作流的本地软件。系统以受限 Mermaid flowchart 描述角色职责和角色间交接，编译为语义中间表示，再由图运行时按顺序、分支、并行、汇合和循环语义调度角色执行。软件提供命令行接口和浏览器可视化控制台。

本版本主要用于本地项目工作流编排和运行控制，不提供跨主机分布式运行，也不将子系统递归嵌套为运行单元。模型调用通过已安装并由用户配置的本地 CLI 服务执行；OGSystem 不导入或托管模型服务凭据。

项目按目录独立保存定义、执行配置和运行数据。首次使用时应在专用工作目录中创建项目，并确认当前终端位置与项目根目录一致。不要在多个项目之间共用同一个 `.ogs/` 数据目录，以免把运行记录和工作流定义混淆。

首次打开控制台时，先从项目列表确认当前项目名称和根目录，再进入工作流视图检查角色节点与交接关系。若项目尚未初始化，应先完成初始化并保存定义；不要在错误目录下创建第二份配置来绕过加载问题。

## 2. 运行环境

- Windows、macOS 或 Linux。
- Node.js 22.x 或 24.x。
- pnpm 10.33.2，或使用 npm 安装。
- 使用实际模型执行时，需安装并配置对应的模型 CLI；干运行和结构校验不要求模型凭据。

运行时应使用受支持的 Node.js 主版本，并在安装前确认当前用户对项目目录具有读写权限。项目运行期间需要保留 `.ogs/` 目录；删除该目录会同时删除本地运行状态和审计数据。升级前应按组织的数据保留规则备份仍需留存的运行记录。

## 3. 安装与创建项目

从源码目录安装：

```text
npm install -g .
```

创建最小项目：

```text
ogs project create demo-app --template minimal
cd demo-app
```

项目主要包含 `system.mmd` 工作流定义、`.ogs/` 控制与运行数据目录、`og-roles/` 角色说明和执行配置。使用 `ogs project init` 可在当前目录初始化项目。

项目创建后先查看工作流文件和角色目录，确认示例角色与当前任务相符，再替换任务输入和角色说明。角色配置应保持职责清晰，并声明可接受的输入、预期输出和执行器；不要把访问密钥或个人凭据写入角色提示词或版本控制文件。

在共享项目或从归档恢复项目时，先确认依赖、运行配置和模型执行器与当前机器匹配。模型执行器不可用时仍可进行静态检查和干运行，但真实模型调用不会成功；应先恢复执行环境再提交真实运行。

## 4. 工作流建模

打开 `system.mmd`，使用 Mermaid `flowchart` 的受限子集描述角色节点及角色间交接。节点表示承担稳定职责的角色席位；连线表示角色完成职责后的交接，连线标签承载事件或交接结果。每个角色配置输入、输出和执行器绑定；事件契约用于约束角色间数据传递。

编辑后先执行校验或干运行，查看结构错误、合同错误和运行轨迹，再进行真实模型运行。系统设计器提供图形编辑、合同配置和结构化校验入口。

校验工作流时，应检查每个角色是否有明确的出边或终止条件，分支事件是否能由上游角色产生，汇合节点是否等待预期的输入，以及循环是否具有退出路径。合同字段名称、类型和必填约束应与角色实际输出一致；修改合同后应重新校验，不要依赖模型自行补齐结构错误。

使用图形编辑器时，保存修改后查看校验结果摘要和具体节点定位。错误应在发起真实运行前处理；警告则应结合工作流目标判断是否接受。重要修改应先在副本或版本控制分支中验证，避免覆盖正在使用的项目定义。

## 5. 启动和运行

干运行示例：

```text
ogs run start --system system.mmd --input "smoke" --dry-run
```

真实运行时去掉 `--dry-run`，并确保所选模型 CLI 已安装、已登录且可调用。系统会创建运行 ID，并将阶段、角色执行结果和审计信息保存在项目的 `.ogs/runs/` 目录。

常用命令：

```text
ogs run list
ogs run status <run-id>
ogs run logs <run-id> --engine --tail 50
ogs run resume <run-id>
ogs vis --ogs-dir .
```

## 6. 可视化控制台

使用 `ogs vis --ogs-dir .` 启动本地控制台。在项目视图中可以检查工作流图、配置角色、校验结构、启动干运行或真实运行。运行视图用于查看状态、时间线、日志、产物和待处理人工审核。

启动真实运行前检查项目路径、输入内容、模型选择和运行模式。列表中的状态和操作以当前运行记录为准；页面提示的“已记录”表示决定已写入控制面，不一定代表运行时已完成后续恢复。

开始运行前，先确认输入没有无关的个人或机密信息，并检查模型选择与当前角色执行器绑定一致。干运行适合检查路由和流程结构，不代表模型输出质量已验证。真实运行启动后记录运行 ID；后续查看状态、日志或恢复时应使用同一个 ID，并确认界面当前展示的是目标项目。

运行详情中的阶段列表用于了解角色开始、完成和交接顺序；日志用于定位单个执行步骤；产物用于查看已保存的输出。若状态为执行中，应先确认当前执行是否仍在推进；若为等待审核，则需处理对应审核项；失败状态应结合错误信息和最后成功阶段判断是否可安全恢复。

## 7. 人工审核与恢复

当流程要求人工审核时，运行会暂停并显示待审内容、角色、分支和决策草稿。审核人可选择批准、要求返工、暂停或终止，并填写说明该决定依据的理由。理由必须非空，最多 2000 个字符；不能只填“同意”“通过”等结论词，也不能保留模板提示。确认前可以复核并修改理由。提交成功后决定进入审计记录；需要继续执行时，使用界面的恢复操作或 `ogs run resume <run-id>`。

审核前先阅读完整草稿、关联角色和分支信息，并核对本次审核属于哪个运行和哪一轮。批准表示接受当前草稿并允许流程继续；要求返工表示将工作退回指定角色；暂停用于保留当前状态以便稍后处理；终止会结束配置范围内的执行。填写与所选决定对应的事实、依据和风险，不要把模板文本当作审核说明。

提交前检查确认页中的决定类型和理由。若校验失败，按页面提示修正理由后再次确认；校验失败时决定不会提交。浏览器可保存未提交的理由草稿以便继续编辑，但草稿保存不等于审核已完成，也不会自动批准、返工、暂停或终止运行。提交成功后应在审核历史中确认决定和理由已记录。

重新恢复前核对运行 ID、待审决定和恢复就绪状态。恢复依赖持久化检查点及执行记录，以避免重复执行已持久化的角色工作。终止操作应检查其作用范围是当前分支还是整个运行。

如果运行仍处于等待审核，先完成或明确处理待审决定，再执行恢复。恢复前确认项目目录可读写，运行状态文件和检查点存在，并查看最近一次阶段结果。恢复后检查阶段计数和执行轨迹，确认已经完成的角色没有意外重复运行；不要同时从多个终端恢复同一个运行。

## 8. 状态与数据

运行数据存储于项目 `.ogs/runs/<run-id>/`。其中包括状态快照、执行记录、审核记录、日志和产物索引。运行状态用于区分执行中、等待审核、暂停、完成和失败。审计记录保留执行器、模型、事件、时间和结果摘要等运行信息。

项目目录可能包含提示词、输入和模型输出。使用前应按组织的数据保留与访问控制要求保护目录，并在对外分享前检查敏感信息。

需要归档时应保留与目标运行对应的完整目录结构，不要只复制单个状态文件。清理旧运行或快照前先核实保留策略和待审核状态；被删除的数据可能无法通过界面恢复。日志、审核理由和模型输出也应按其内容级别管理访问权限。

## 9. 常见问题

- 无法创建或加载项目：确认当前目录、`system.mmd` 路径及 `.ogs/` 配置是否有效。
- 真实运行失败：检查所选模型 CLI 是否已安装、认证状态是否有效，以及本地运行权限和网络策略。
- 运行等待审核：这是流程定义的人工门控状态；完成审核后再恢复运行。
- 恢复被拒绝：检查运行目录内的持久化状态和诊断信息，不要手工修改状态文件后继续执行。
- 审核理由不接受：移除空白和模板说明，填写与当前决定有关的具体依据；确认页仍可编辑该文本。

页面内容与命令行结果不一致时，先刷新项目和运行详情，再核对运行 ID 与更新时间。若服务无法访问，确认本地 Visualizer 进程仍在运行、端口未被其他程序占用，并从正确的项目目录启动服务。修复服务后再次检查 `/healthz` 与 `/readyz`，再继续任何会改变运行状态的操作。

当角色输出不符合预期时，分别检查工作流路由、角色提示、输入材料、执行器选择和事件合同。调整其中一项后重新进行结构校验和干运行；确认流程按预期路由后再做真实模型运行。保留失败日志和运行 ID，便于复现问题和审查处理过程。

## 10. 功能边界

软件使用本机文件系统保存项目和运行记录，调用用户本机已配置的 CLI。软件不提供模型服务账户、密钥托管、跨主机分布式执行或组织级身份认证服务。执行能力和数据访问范围受本机账户及外部 CLI 配置约束。
