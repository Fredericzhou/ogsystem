# 面向社会分工协作的设计理念

> **实现状态：** 本文描述 Team IR v2 的提案能力与设计边界，不代表当前发布版本已经实现。可用能力以 v2 完成实现、验收和发布说明为准。

## 我们建模什么

社会协作依靠分工：不同岗位承担不同责任，按约定交接信息与成果，在需要时并行处理，在关键决策前复核，最后由明确责任方形成对外结果。协作可靠与否，往往取决于责任边界和交接质量，而不是参与者数量。

Team IR 将这类协作表达为一组可检查、可运行、可追溯的责任关系。它关注“谁负责什么、需要什么输入、交付什么结果、何时交给谁、如何汇总和结束”，不试图把整个组织或社会压缩成一张自动化流程图。

## 设计原则

| 社会协作实践 | Team IR 的设计对应 | 带来的保障 |
| --- | --- | --- |
| 按专业分工 | Agent 声明职责、输入端口和输出事件 | 责任和交付形状可检查，避免把所有工作塞进一个万能角色 |
| 有凭据地交接 | Handoff 明确发送方、接收方、字段映射和 Artifact | 业务字段与材料按需映射、交接过程可审计；共享 task 是所有 Agent 可见的公共上下文 |
| 先分派，再协作 | Orchestration 将路由条件与数据合同分开 | 控制流可理解，业务数据映射不必混入执行引擎细节 |
| 多人分头处理，由归口者汇总 | 静态 fan-out、`all_of`/`quorum_of` Join 和汇总 Agent | 专家可以并行工作；最终交付完整且唯一，需要合并的材料先交给明确的汇总责任方 |
| 重要事项需要复核和返工 | Runtime 审核门、`draft`/`revise` 端口和 `$.loop.previous` | 审批可以暂停、留痕、限时；返工只引用紧邻上一轮的唯一成功输出，不混读更早版本 |
| 结案必须清楚 | `runResult`、唯一结果写入和 Run 完成条件 | 不把某个分支提前结束误当作整个工作已完成 |
| 档案按需调阅 | 每次 Agent attempt 的 Artifact 读取白名单 | Agent 只能通过受控 Resolver 读取本次交接给它的材料；文件编号本身不代表访问权限 |
| 复工要确认依据未变 | `compiledPlanDigest` 和运行检查点 | Schema、角色包、Binding 或编译语义变化时，不会静默用新规则续跑旧任务 |

### 交接历史与角色记忆

共享的 Run `task` 是所有 Agent 可见的不可变公共上下文。某个 Role 在前一轮产生的草稿、测试结果或审核意见，只有在 Team IR 通过 Handoff、Loop 上一轮引用或 Artifact 显式交付时，才成为后续调用的输入。`$.loop.previous` 只提供同一 Loop Scope 和 lineage 中紧邻上一轮的成功输出；Runtime 不自动注入完整对话历史或累计所有审核反馈。

Team 可以把需要保留的工作记忆声明为端口 Schema 中的普通字段，例如未解决缺陷、已尝试修复和最近测试结果，再由 Role 输出并映射到下一轮。这样的记忆是可检查、可持久化的业务状态。底层模型 session 是否复用属于 Binding 实现细节，不构成 v2 的默认 Role 记忆语义；正确性不得依赖未声明的 session 历史。

## 典型场景

### 市场研究与报告

研究团队分别收集客户需求、竞品信息和行业数据。汇总 Agent 检查材料完整性、解决字段冲突并形成统一报告，再通过唯一结果通道交付。若需要管理者签发，审核门在最终路由前暂停，审核意见进入明确的返工端口。

适用价值：专业工作可并行，结果合同让报告有固定形状，来源 Artifact 保留证据链，审核和返工有明确记录。

### 采购与供应商审查

采购申请进入后，财务、信息安全和法务按各自职责评估。财务必审材料由保证到达的来源提供；法务或安全按条件参与时，只提交 optional 意见。`all_of` 等待所有来源明确到达或跳过，必需贡献缺席立即失败，optional 条件意见可合法省略；`quorum_of` 用于有明确人数门槛的专家评估。汇总责任方形成建议，授权人员作最终决定。

适用价值：各专业可以只提交自己负责的材料；汇总阶段检查必需项；系统记录每项材料的来源和缺项原因。

### 客户问题与服务升级

入口先按问题类型和严重程度分流，再交给客服、技术支持或计费岗位。技术问题可在诊断与日志收集之间并行；无法解决时进入人工升级。对客户的最终答复由指定责任方汇总，避免多个处理分支分别给出互相矛盾的承诺。

适用价值：问题去向明确、未解决事项不静默消失、升级路径可检查，客户答复保持单一归口。

### 生产事件响应

值班人员确认事件后，诊断、影响范围分析和缓解方案评估可以并行。具有风险的操作先暂停在审批门；审批通过后才启动执行 Handoff。事件结束后，由复盘责任方汇总时间线、影响和后续行动。

适用价值：高风险动作受人类控制；审批时间与执行预算分开；行动来源、批准记录和结果可用于复盘。

### 合同或政策文件审核

条款提取、政策比对和风险识别由不同专业角色完成。汇总者按条款编号合并意见，重复字段或缺少必审意见会阻断交付。法律效力、签署权和最终解释权仍归有权限的人。

适用价值：将可重复的材料整理和检查流程结构化，同时保留人类承担判断与授权责任。

### 外部团队待补件

远程协作方通过 A2A 表示需要补充输入时，Run 进入 `paused_input_required`，保存待补件请求并允许调用方取消。v2 不承诺向原远端任务补丁续接；发起方调整材料后创建新 Run。

适用价值：把外部等待变成可查询的工作状态，不把未解决请求误记为成功，也不把不同任务的上下文混在一起。

### 阶段门禁与提前止损

立项初筛、授信或投资审查可由初审角色输出 `PASS` 或 `REJECT_EARLY`。通过路径启动后续并行尽调；拒绝路径直接交付完整的驳回结果，不激活下游专家。每条结案路径必须独立满足 `runResult`，互斥路由保证一次 Run 只写入一个结果。

适用价值：在高成本工作开始前设置明确的判断点，及时停止不符合条件的项目。

### 四眼原则与独立核对

财税、医疗或工程校审可以串联 Maker 和 Checker，不通过时按类型化反馈进入返工 Loop；也可以将同一凭证映射给两个独立计算角色，再由 Reconciler 通过 `all_of` Join 比对差异。需要合并多方材料时先由核对角色汇总，再交付唯一结果。

适用价值：职责分离和独立计算路径明确；系统能够暴露差异与缺项，但专业结论和签署权仍由具备权限的人承担。

### 跨层级分包

总项目可将研发、法务和市场等职能交给独立子服务处理，再接收各自的标准化结果。若子团队部署了 A2A Agent Card 外观并提供兼容的输入/输出合同，上层 Team 可将其当作远程 Agent 调用。

适用价值：上下层按合同交接、分别演进，避免一张图包含所有基层步骤。Team IR v2 本身不定义子 Team 自动发布为 A2A Agent；这需要独立的服务封装、部署和运行治理。

## 信息隔离与结构化博弈

相同的分工机制也能组织固定参与者、有限回合的对抗或博弈流程。系统负责控制交接范围、轮次和结算顺序；它不替代博弈规则，也不保证参与者的策略行为。

| 场景 | 可表达的协作结构 | 重要边界 |
| --- | --- | --- |
| 按需会签 | 财务必审来源提供 required 项；法务、信息安全按条件提供 optional 意见；`all_of` 汇总后交给归口人 | 必审材料必须保证到达；条件来源只能贡献 optional 项；至少有实际到达的 Join 来源 |
| 盲拍或重复博弈 | 裁判把各自输入投影给独立参与者；各方决策后汇入裁判结算；有限 Loop 表达回合 | 共享 `task` 不能含任何一方的秘密；显式映射不是密码学隔离，不能保证参与者无法推断或串通 |
| 双盲评审、红蓝对抗 | 两个独立分支读取经脱敏的同一材料，互不接收对方意见；主编或裁判汇总后决定是否返工 | 作者信息必须从输入和 Artifact 中实际移除；不能保证无法从文风、上下文等线索推断身份 |
| 固定 roster 的主持人博弈 | 主持人按不同视角投影材料；淘汰席位通过条件 Handoff 跳过 optional Join 贡献；回合由 Loop 管理 | 参与者和拓扑需预先声明；零存活席位时主持人须直接输出 `GAME_OVER` 结案，不能派发后进入零到达 Join；不负责游戏规则的公平性证明 |

这些模式体现了 Team IR 的控制面价值：裁判、主编或主持人的汇总职责明确，未选中的交接不会凭空发生，规则允许的缺席与必须到达的意见有不同处理。它们不是保密协议：`$.run.task` 对 Agent 可见，Team 作者可以选择把某项数据映射给任何角色。需要严格信息隔离时，应将秘密放在独立 Run 或受控外部服务中，并由身份/信息流策略或密码学机制约束访问。

固定 roster 的回合实现中，主持人的初始化执行作为 Loop Scope 的首轮入口并发出第一次 `DISPATCH`；每个 `round_collect` Join 的 `baseMapping` 单独提供 required `prevState`，可以读取通过支配检查的 `$.loop.previous.moderator.*`。各席位入边只映射自己的 optional action，避免重复写入共享状态。主持人若在派发前判定无人存活或胜负已分，应直接输出 `GAME_OVER` 并交付结果；若派发后所有席位都跳过，Join 按规则以零到达失败，不会伪装成正常结算。

## 系统提供的价值

- **降低协调成本**：交接字段、责任端口和路由规则集中表达，不需要依赖隐含共享状态或口头约定。
- **减少遗漏**：必填合同、Join 来源状态和结果完成规则让缺项显式失败，而不是以“流程跑完”掩盖未完成工作。
- **支持并行但保持归口**：独立任务可以并行，最终交付要求完整且唯一；需要多方合并时先汇总，再对外结案。
- **提升可追溯性**：Handoff、Artifact 来源、审核意见和检查点构成可复核的工作记录。
- **减少不必要的数据暴露**：每次调用按显式映射获得输入与 Artifact 能力，便于检查谁会收到什么；强保密仍需身份和信息流策略。
- **让复工有依据**：恢复前确认编译依赖闭包一致，避免岗位说明、验收标准或执行策略变化后沿用旧任务状态。
- **保留人类决策权**：审核超时失败关闭；系统可以组织材料和执行获批的动作，但不把模型输出伪装成人类授权。
- **让等待可管理**：审核门有独立超时；等待期间暂停活跃执行预算，审核完成后才开始下游 Handoff 的交付时限。

## 适用边界

Team IR 最适合责任角色相对稳定、交付可描述、交接可校验、流程可以重复执行且循环有界的协作任务。它也能表示有限的分支、并行、汇总、人工审核和返工。

结果必须按 `executionPolicy.resultMode` 明确选择必需交付或允许空结果。Run 只有在所有活动分支、Join、Loop 和审核门都已收敛，并满足结果策略后才算完成；分支结束不等于项目结案。

它不是组织结构图、劳动关系模型、权限系统或共识算法。它不自动解决信任建立、权力制衡、利益冲突、法律责任、价值判断、非正式协商和动态组队。身份认证、审核授权、长期知识治理、数据保留和跨组织合同应由相应的控制面与领域系统负责。

### v2 首版暂不覆盖

| 人类协作模式 | 首版边界 | 可行替代或后续方向 |
| --- | --- | --- |
| 运行时动态 Map-Reduce | 拓扑和 fan-out 目标静态声明，不按运行时数组动态创建 Agent 调用；Artifact 槽位首版为 `single` | 使用有限个预声明槽位，或由单个 Agent 在内部处理集合；后续评估动态集合 fan-out 与多 Artifact 合同 |
| 故障后图内自动顶岗 | Binding 可按自身合同重试；只有明确支持时才可使用模型/服务层 fallback。Run 级没有可路由的 ERROR 边，已激活分支失败仍失败关闭 | 将供应商或模型容灾配置在支持该能力的 Binding/网关；图内补偿和顶岗路由留待后续设计 |
| Pull-based 抢单池 | Handoff 静态指定接收 Agent，不支持由空闲坐席竞争领取任务 | 由上游队列或网关选定坐席，再将交付发给图中的职能 Agent |
| 多人共享可变白板 | 不提供多个 Agent 无序并发读写的全局共享状态 | 使用主持人汇总的 Hub-and-Spoke 多轮征询、显式字段映射和 Join |

判断一个场景是否适合建模，可以先问：参与角色是否明确？交接内容能否说清？缺项和完成如何判定？哪些步骤必须由人批准？如果这些问题有稳定答案，Team IR 能把协作规则变成可验证的运行合同；如果核心工作是开放式协商或依赖现场裁量，系统应支持人参与，而不应把它强行自动化。

架构取舍和 Join/Loop 的精确定义见[Team IR 协作边界 ADR](../development/adr-team-ir-collaboration-boundaries.md)与[Team IR v2 Handoff 设计方案](../development/team-ir-handoff-v2-design.md)。
