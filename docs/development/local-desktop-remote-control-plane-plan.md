# 本地桌面端与远程控制面规划

状态：规划中。本文描述目标架构，不代表当前仓库已经提供 Electron 桌面应用、独立门户或远程配置服务。

## 目标

- 提供独立门户，承载产品介绍、文档、桌面软件下载、版本说明和更新入口。
- 让 OGSystem Runtime 和业务执行在用户本机运行，直接访问用户授权的项目目录与本地工具。
- 通过远程服务管理账号、授权、组织策略和已发布团队配置。
- 保持本地已有项目在网络中断时可用；远程服务不可用时，不影响已下载配置的本地运行。
- 将本地敏感数据默认留在本机，只有用户明确启用同步或组织策略要求时才上传。

## 现状与边界

当前 OGS Studio 与 OGS Projects 共用 Team Site 的 Origin、SPA Shell 和服务进程。Team Site 同时处理 Studio、Projects、Platform 等页面及相关 API。仓库已有可本地运行的 OGSystem Runtime 和 CLI，但尚无 Electron 桌面产品、独立门户服务或远程配置控制面。

目标方案不要求立即拆分现有 Studio。门户和桌面应用先作为新入口建设，通过稳定 API 与远程服务交互；当前 Team Site 可在迁移期继续提供 Studio、Projects 与其现有 API。后续按业务边界逐步拆分服务，避免门户部署与 Studio 发布绑定。

## 目标架构

```text
portal.example.com
  产品介绍、文档、下载、版本说明
  静态托管/CDN

downloads.example.com
  Electron 安装包、签名、校验和、更新清单
  对象存储/CDN

control.example.com
  账号、授权、组织、配置目录、版本与审计 API

用户设备
  Electron 桌面壳
    本地 Web UI
    安全的 preload 能力桥
    本地 API / Runtime 子进程
    本地项目、凭据引用、运行记录
```

门户、下载服务、远程控制面和本地执行端分别发布。门户与下载服务故障不应影响 Studio 或本地 Runtime；控制面不可用时，本机仍可运行已有的本地项目和已同步配置，但登录续期、授权校验策略要求的在线操作、拉取新配置和软件更新会受限。

## 职责划分

| 能力 | 所在位置 | 说明 |
| --- | --- | --- |
| 产品介绍、文档、下载入口 | 远程门户 | 优先静态托管，不承载 Runtime 执行。 |
| 安装包与自动更新文件 | 对象存储/CDN | 发布签名安装包、版本元数据、校验和及更新清单。 |
| 登录、组织、席位和授权 | 远程控制面 | 通过短期令牌识别用户；客户端包内不得包含服务端密钥。 |
| Team 模板与发布版本 | 远程控制面 + 本地只读副本 | 远程维护权威发布版本；本地缓存已下载版本并固定摘要，运行时不依赖远程读取。 |
| Team 草稿和发布准备 | 本地优先，可选远程协作 | 支持本地编辑；需要多人协作时再同步草稿，并定义并发冲突处理。 |
| 项目目录、材料和工作区 | 本地 | 仅访问用户明确选择并授权的目录。 |
| Runtime、Simulation 和本地工具 | 本地 | 由本机进程执行，访问本地 CLI、模型工具或工作区。 |
| 本地模型推理 | 本地 | 适合数据不出设备的场景，受本机 CPU/GPU、内存和模型体积限制。 |
| 云模型推理 | 云服务商或受控代理 | 发送模型请求所需的提示词与材料；界面和策略需明确披露数据去向。 |
| API 密钥与登录凭据 | 本地系统密钥链，或远程服务端 | 本地凭据使用 macOS Keychain、Windows Credential Manager、Linux Secret Service 等安全存储；不能把长期共享密钥打包进应用。 |
| 运行证据和结果 | 本地，选择性同步 | 默认保存在项目 `.ogs/` 目录；支持用户选择同步摘要或指定产物。 |
| 产品遥测 | 可选远程 | 默认最小化，不上传提示词、材料、密钥或完整运行内容；提供组织策略和用户可见设置。 |

## 核心数据流

### 下载与更新

1. 用户从独立门户选择适配操作系统的安装包。
2. 安装包和更新由发布流水线签名，并生成校验和及版本清单。
3. 桌面应用只接受可信发布渠道、有效签名和满足版本策略的更新。
4. 更新下载与安装不依赖 Studio 的页面服务。

### 远程配置到本地运行

1. 用户在远程控制面发布不可变 TeamVersion。
2. 桌面端通过认证 API 拉取版本元数据和配置包。
3. 本地校验签名/摘要、兼容性和授权范围，展示版本及变更摘要。
4. 用户或已配置组织策略确认后，将配置写入本地缓存。
5. Run 固定配置版本与摘要，在本地 Runtime 执行并记录实际解析配置。
6. 若启用同步，按策略上传经过用户确认的摘要或选定证据；本地原始材料不默认回传。

远程更新不应静默覆盖用户本地草稿。发布配置作为不可变版本导入；本地修改应形成草稿或派生版本，并通过显式合并/发布建立新版本。

### 本地与云模型

- 本地模型和本地 executor 不经过门户服务；桌面端调用本机已安装且已登录的工具。
- 云模型请求需要访问模型服务。可由本地客户端直连模型提供商，也可经远程代理统一计费和策略控制。
- 直连模式下，提供商凭据保存在系统密钥链中；代理模式下，长期提供商密钥只留在服务端，客户端使用短时、限权令牌。
- 两种模式都应清晰显示请求会发送到的服务和数据范围，并避免将密钥、提示词或完整材料写入普通日志。

## 性能与安全原则

- 大文件、项目材料、运行状态和执行产物留在本地，避免不必要的上传、下载和序列化开销。
- 远程 API 传输账号、授权、版本元数据和用户选择同步的内容；配置包应可缓存并按摘要寻址。
- 本地服务仅绑定 loopback 地址，使用随机端口或进程间 IPC；拒绝来自非本机的连接，并校验本地请求来源/令牌。
- Electron 窗口启用 `contextIsolation`、关闭 `nodeIntegration`、保持 renderer sandbox；通过 preload 仅开放窄范围、逐项校验的能力。
- 禁止任意网页导航获得本地能力；外部链接交给系统浏览器打开。设置严格内容安全策略，并限制允许加载的远程 Origin。
- 对目录访问采用用户选择授权和路径约束；危险操作与外部副作用应在应用内明确呈现。
- Electron 应用内代码和已下发配置都可被本机用户检查。代码签名、asar、混淆和加密存储不能构成本机所有者面前的保密边界。
- 本地凭据按最小权限和短时有效设计，支持撤销；日志脱敏。管理员权限或终端已被攻陷时，不承诺本地秘密绝对安全。
- 离线运行遵循明确的授权缓存期限和组织策略；到期后的行为需产品决策，不能隐式删除或破坏本地数据。

## 独立门户与服务部署

| 服务 | 建议形态 | 依赖关系 |
| --- | --- | --- |
| 门户 | 静态站点/CDN | 不依赖 Studio 进程。 |
| 下载与更新 | 对象存储/CDN + 发布元数据 | 由桌面发布流水线更新，不要求 Studio 同步发布。 |
| 控制面 API | 独立部署的 Web API | 提供身份、授权、配置目录和审计能力；不执行用户项目。 |
| Studio / Projects | 现有服务，后续可独立演进 | 保持现有用户入口；可逐步消费共享身份与发布配置 API。 |
| 本地 Runtime | Electron 管理的本地进程或原生模块 | 无门户依赖；本地文件访问只在本机授权范围内。 |

域名仅为示意。生产部署应按现有身份系统、网络和运营要求确定 Origin、CORS、Cookie/令牌策略、数据区域与备份方式。

## 分阶段实施

### 阶段 0：边界与威胁模型

- 盘点现有 Team Site API、文件存储、Runtime 启动方式、凭据来源和已有 package 格式。
- 确定远程配置对象、不可变版本、签名/摘要、兼容性和回滚契约。
- 明确组织授权离线策略、模型请求数据策略、同步范围与保留期限。
- 产出 Electron IPC 能力清单和本地服务威胁模型。

### 阶段 1：独立门户与下载

- 新建门户应用和独立部署流水线，不更改现有 Studio 路由及发布流程。
- 建立桌面发布元数据、安装包存储、校验和、代码签名和版本说明页面。
- 下载站故障不应影响 Studio；门户不直接承担产品 API 数据读写。

### 阶段 2：桌面壳与本地 Runtime

- Electron 加载本地构建的 UI，使用安全 preload/IPC。
- 由主进程管理本地 Runtime 生命周期、用户选择的项目目录和应用更新。
- 复用 OGSystem CLI/Runtime；不要在 Renderer 中直接获得 Node.js 或 shell 权限。
- 支持本地配置、Simulation 和运行证据，不要求远程账户才能完成基础本地运行（最终授权策略另行确认）。

### 阶段 3：远程账号与只读配置同步

- 增加控制面认证、组织授权和 TeamVersion 只读下载 API。
- 桌面端实现配置包校验、缓存、变更预览和显式导入。
- 先实现单向“远程发布版本 -> 本地副本”，暂不引入双向草稿同步。

### 阶段 4：可选协作和结果同步

- 再定义草稿协作、合并冲突和审计事件契约。
- 允许用户/组织策略选择性同步运行摘要或产物。
- 增加撤销、删除、保留期限、导出和跨设备恢复能力。

## 主要决策与待确认项

- 桌面端目标操作系统及首发顺序（Windows、macOS、Linux）。
- 用户是否必须登录才能使用本地 Runtime；离线授权最长有效期及到期行为。
- 远程配置首期范围：仅 TeamVersion，还是也包含模型引用、工具元数据、组织策略。
- Team 草稿是否需要多人远程协作，或先保持本地编辑、发布后分发。
- Project Run 和 Simulation 是否始终只保存在本地，或支持按项目选择云同步。
- 云模型采用用户自有凭据直连，还是组织集中代理；数据保留与区域要求是什么。
- 是否允许自动更新，组织管理员能否固定版本或延迟升级。
- 本地 Runtime 是否作为独立进程通过 loopback HTTP 暴露，或使用 Electron IPC/子进程标准输入输出。

## 验收标准

- 门户、下载与更新服务可独立发布；发布门户不会重启或更改 Studio。
- 用户可以从门户下载经过签名和校验的桌面包，并验证版本与发布者。
- Renderer 无法直接访问 Node.js、任意 shell 或未授权文件系统能力。
- 本地 Runtime 可对授权目录执行本地项目；远程控制面短时不可用不影响已有配置的运行。
- 远程配置导入校验签名/摘要并固定版本；失败或取消导入不会覆盖本地草稿。
- 默认运行过程不上传项目材料、提示词、密钥或完整运行证据。
- 云模型调用和任何同步行为有可见的数据去向、范围、授权与失败反馈。
- 更新失败、签名无效、磁盘空间不足或应用回滚时，不损坏本地项目和运行证据。
